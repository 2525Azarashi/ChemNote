# 構造の整理（リファクタリング）の記録

アプリ内部構造の整理について、**何を直したか**と、
**何をあえて直さなかったか（その理由）** をまとめたものです。

このファイルの目的は「次に同じ場所を見た人が、もう一度同じ調査をしなくて済むように」です。
とくに後半の「あえてまとめなかったもの」は、
似ているコードを見つけたときに「これは前に検討して、まとめない結論が出ている」と
分かるようにするためのものです。

---

## 0. 前提（混同しないこと）

- **ビルドが落ちる問題（OOM）は、この構造整理とは別の話です。**
  原因はサンドボックスのメモリ不足で、コードの構造ではありません（`docs/BUILD.md`）。
  構造を整理すれば OOM が直る、という関係にはありません。
- 整理の目的は「同じ内容を2か所以上で直さなくて済むようにする」ことだけです。
  **UI・デザイン・表示内容は一切変えていません。**

---

## 1. 進め方（毎回この順でやっています）

1. 重複や依存の問題を探す
2. **まとめる前のコードをテストに写す**（`legacy〜` という名前で残す）
3. ★写した昔のコード同士を突き合わせる★
   → ここが一致しなければ「まとめてはいけない」という判断になります
4. 実装前にテストを走らせ、**構造の見張りだけが落ちる**ことを確認する
   （落ちないテストは、書いても意味がないので）
5. 実装する
6. `npx tsc --noEmit` → `npm run build` → テスト全体
7. **本物のデータで出力を丸ごと書き出し、変更前後で1バイトも違わないことを確認**
8. スマホの画面（390×844）で実際に触って確認

### なぜ「本物のデータで突き合わせる」のか

テスト用の小さなデータだけだと、
現実のデータにしか出てこない分岐を通らないことがあります。
そのため、本物の章データを使って出力を全部ファイルに書き出し、
変更前と変更後で MD5 が一致することまで確認しています。

---

## 2. まとめたもの（実施済み）

いずれも「同じ内容が2か所以上に書かれていて、
**片方だけ直すと不整合が起きる**」ものです。

| 内容 | 置き場所 | 確認したこと |
| --- | --- | --- |
| 章ID → ツリーの対応表 | `src/data/chapterTreeMap.ts` | 表示が変わらないこと |
| 短答式サブ設問の組み立て（`sq`） | `src/data/mathProblemKit.ts` | 171箇所ぶんが同一 |
| HTML エスケープ | `src/utils/sanitizeHtml.ts` | — |
| 復習の3操作（正解・不正解・削除） | `src/utils/reviewList.ts` | — |
| 化学2教科の解説の後処理 | `src/data/explanationPostProcess.ts` | 194問 / 16,735行が同一 |
| 英語2教科の解説の後処理 | `src/data/listeningPostProcess.ts` | 64問 / 6,182行が同一 |
| 学習指標の導出（5指標） | `src/utils/studySummary.ts` | 6教科 × 生徒12人 / 8,413行が同一 |
| CSV の骨組み（BOM・CRLF・エスケープ） | `src/utils/studySummary.ts` | 4種の CSV / 8,795行が同一 |

### 置き場所についての注意

共通処理を `src/utils/` に置くと、
`utils → data → utils` という往復（循環依存）が生まれることがあります。
そのため解説の後処理などは、あえて **`src/data/` の中**に置いています。
「共通だから utils」と機械的に決めていません。

## 3. ★あえてまとめなかったもの★

「似ているから1つにする」は、いつでも正しいわけではありません。
以下は検討した上で、**まとめない**と判断したものです。
再検討する場合は、ここに書いた理由が変わっているかを先に確認してください。

### 3-1. 化学の解説の後処理 ↔ 英語の解説の後処理

見た目は似ていますが、**分岐が違います。**

- 化学：構造化解説には補足（`explanationSupplement`）を足し、
  `teaching` と単位変換を渡す
- 英語：構造化解説はそのまま通し、まずリスニング専用の組み立てを試す

まとめると、どちらかの教科で**解説の並び順が変わってしまう**ため、
2つの関数のまま残しています。
`tests/listeningPostProcess.test.ts` に、
この2つが混ざっていないことを見張るテストを入れてあります。

### 3-2. `MathProblem` / `AdvancedProblem` / `BiologyProblem`（型3つ）

中身は3つとも同一です（`id` / `category` / `text` / `subQuestions` /
`explanation` / `surroundingKnowledge` / `deepDiveTopics`）。
それでもまとめていない理由：

1. **3つのファイルはどれも何も import していない「葉」です。**
   共通の型ファイルを作って import させると、
   葉ではなくなり、`data` 層の内部に新しい依存の線が増えます。
   今は `index → data` の一方向で、`data` は何も import しない状態を保てています。
2. **同じ形のままとは限りません。**
   実際に、英語の `GrammarProblem` と `ListeningProblem` は
   同じ出発点から `audioTracks` と `readCount` が追加され、既に形が違います。
   教科ごとに増える項目が違うので、
   1つの型に固定すると、後から教科固有の項目を足しにくくなります。
3. 型が一致していないと `tsc` が落ちるので、
   **ずれても気づけない類の危険がありません。**
   （CSV の BOM やエスケープのように「黙って壊れる」ものとは性質が違います）

つまりこれは「綺麗にするためだけの分割」に当たるため、やりません。

### 3-3. `ReviewList.tsx` / `NoteList.tsx` の JSX

`StudyHub.tsx` と似た見出し・戻るボタン・バッジのJSXがありますが、

- **`ReviewList.tsx` と `NoteList.tsx` はどこからも表示されていません**
  （ホームの「ノート」は `study_hub` に飛び、`StudyHub.tsx` が表示されます）
- 使われていないのでビルド時に取り除かれ、利用者には影響しません

**消してはいません**（消すと機能を削ることになるため）。
表示されていないファイルのために共通部品を作るのは、
「綺麗にするためだけの分割」なのでやりません。

### 3-4. `Explanation.tsx` / `Quiz.tsx` の選択肢リストの JSX

`<li>` の見た目は同じですが、渡している中身が違います。

- Quiz：`formatText(row.body, combinedHighlights)`（正誤のハイライトを渡す）
- Explanation：`formatText(row.body, [], { prose: isEnglishChapter })`（英語は散文で組む）

さらに `ExplanationBody` に渡す props も違います（`highlights` ／ `tone` + `prose`）。
共通部品にすると引数が増えて条件分岐が中に入り込み、
かえって「どちらの画面の話なのか」が読み取りにくくなります。
見た目が同じだけなので、まとめません。

## 4. 直していない既知の問題（別の話として記録）

構造整理の途中で見つけたものです。
**表示が変わるため、今回はあえて直していません。**

### 4-1. 英語の解説の後処理を2回走らせると解説が伸びる

同じデータに対して後処理を2回実行すると、解説が約2倍になります
（実測 1,087字 → 2,568字）。

- ★これは今回の整理で生まれたものではありません。★
  **まとめる前のコードでも、まったく同じように伸びます**（測って確認済み）。
- 汎用の整形エンジンには「もう整形済み」の目印がありますが、
  リスニング専用の組み立てにはありません。それが理由です。
- 実際のアプリは起動時に1回だけ実行するので、表示上の問題は出ていません。
- **勝手に直すと解説の表示が変わってしまうため、直していません。**
  `tests/listeningPostProcess.test.ts` に、
  「変更前と同じ振る舞いであること」として記録してあります。

### 4-2. `localStorage` が使えない環境で画面が真っ白になる

`App.tsx` の状態の初期値で `localStorage.getItem` を直接呼んでいるため、
これが例外を投げる環境（プライベートモード等）では
画面が真っ白になります。

- これも以前からある挙動で、今回の整理とは無関係です。
- 直すと初期表示の挙動に影響が出るため、
  別途あらためて相談してから対応すべき内容として記録しておきます。

### 4-3. `Explanation.tsx` が型を component から import している

`Explanation.tsx` が `NodeData` を `./InteractiveTree`（画面部品）から
import しています。本来は `../utils/logicTreeTypes` から取るのが自然です。
影響は小さいですが、依存の向きとしては望ましくありません。

---

## 5. まだ手を付けていない大きい話（要相談）

以下は「1ファイルが大きい」という話で、**重複ではありません。**

- `Quiz.tsx`（3,707行）
- `Explanation.tsx`（2,516行）
- `App.tsx`（1,014行・`useEffect` が23個）

分けること自体は可能ですが、

- 表示に直結する部分なので、壊れたときの影響が大きい
- 「綺麗にするためだけの分割」になりやすい

ため、**やる前に目的を確認したほうがよい**と考えています。
「どの操作が重いか」「どこを直すのが怖いか」といった
具体的な困りごとが先にあると、分け方を決められます。
