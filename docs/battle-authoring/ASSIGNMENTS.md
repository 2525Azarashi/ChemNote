# 範囲の割り当て台帳（★本体が持つ・これが重複防止の実体★）

## なぜこのファイルがあるのか

作業場（別ルーム）は **PR を出さない**。だから
**「どの作業場がどこをやったか」はどこにも記録されない**。
作業場の自己申告に頼ると、必ず取り合いと重複が起きる。

だから **範囲は本体（人間）が先に切って割り当てる**。
その台帳がこのファイル。**作業場はこのファイルを見ない。**
作業場が見るのは、渡された `PROMPT.md` の §0 の枠だけ。

```
本体（ここ）                    作業場A          作業場B          作業場C
─────────────────────────────────────────────────────────────────────
① 台帳で範囲を切る
② PROMPT.md の §0 だけ書き換えて渡す ──→ 化学基礎前半   化学基礎後半   生物基礎
③                                        JSON を書く    JSON を書く    JSON を書く
④                              ←────── チャットで返す（git 触らない・ZIP 無し）
⑤ 本体が authored/ に格納する
⑥ verify → gen:battle-pool → PR は1つだけ
```

7章だけで 1486 行に達したため。1ファイル 5000 行超になると、編集のたびに
全体を読み直す必要が出て、意図しない箇所を書き換える事故が起きやすくなる。
**新しくファイルを足したら `scripts/lint-chem.mjs` の `TARGET_FILES` にも
必ず追加すること**（入れ忘れると表記ゆれが野放しになる）。

**★着手順の決め方（主観で選ばない）★**
原典の `frequency` と `prediction2027` から機械的に優先度を出している。
超高頻度 100 点／高頻度 70 点／中〜高 55 点／中頻度 40 点／低〜中 25 点／低頻度 10 点に、
予測 ◎ +30 点／○ +15 点を加算した合計の降順。
`a9_5`（錯イオン）は点数では `a9_6` より下だが、原典 `studyPoints` が
「系統分析（a9_6）の前提知識でもある」と明言しているため **先に** 作った。
順序を逆にすると、系統分析の解説で錯イオンを説明なしに使うことになり
学習者が置いていかれる。**点数より学習順序の依存関係を優先する。**

**書くときの原典**: `src/data/chemistryAdvancedTrendData.ts` の
`chapterTrendsAdvanced[].units[].examTypes` と `weapons`。
勝手な知識を作らず、必ずこの原典に実在する武器だけで作問する
（`tests/inorganicProblems.test.ts` が原典との照合を機械で強制している）。

**★解説の見出しの書き方（ここで実際に事故った）★**
解説本文の見出しは「（N）」の直後に**数字を置いてはいけない**。

```
❌ （3）1 mol            ← 見出しと認識されず、解説が画面から消える
✅ （3）硫黄 1 mol から得られる硫酸 → 1 mol
```

`explanationFormat.ts` の `findSubAnchors()` は「(1) が (10) の先頭に
一致する事故」を防ぐため、マーカー直後が数字の行を見出しと認めない。
このため接触法の大問は7小問のうち3小問の解説が丸ごと表示されなくなっていた。
`tests/inorganicProblems.test.ts` の
**「★各小問が自分専用の解説セクションを持っている★」** がこの事故を検出する。

新しい章を収録したら、そのテストの `INORGANIC_DONE` に章IDを足す。

**★小問の `type` に書ける値は3つだけ（ここでも実際に事故った）★**
`type` に書けるのは次の3つだけ。これ以外を書くと `Quiz.tsx` が
描き分けられず、**その小問が画面に何も表示されない**。

```
✅ 'short_answer'      記述で短く答えさせる（列挙もこれ。acceptedAnswers で表記ゆれを許す）
✅ 'multiple_choice'   単一選択（options が必要）
✅ 'descriptive'       記述（gradingCriteria が2件以上必要）

❌ 'multiple-choice'   ハイフンは誤り。アンダースコアが正しい
❌ 'multiple-select'   複数選択は Quiz.tsx が未対応。そもそも存在しない
```

a7_7（気体のまとめ）を書いたとき、実際にこの2つを両方書いてしまった。
当時 `InorganicProblem.subQuestions` は `any[]` だったため **tsc は素通りし**、
`vitest` を回すまで気づけなかった。そこで
`src/data/inorganicProblems.ts` に `InorganicSubQuestionType` を定義して
**tsc の時点で止まる**ようにした（意図的に壊して停止することを確認済み）。

複数を選ばせたい場合は `short_answer` にして列挙を書かせる。
そのとき **単一選択にして答えが他の小問と同じにならないか**を必ず確認する。
a7_7 演習2 では (2) と (3) の答えがどちらも「ソーダ石灰」になり、
(2) を見れば (3) が理解せずに当たる状態になっていたので、
(3) は「いくつあるか」まで書かせる形に変えた。

**★大問を追記するときの配列の閉じ方（3回連続で間違えた）★**
大問を既存の章に追記するとき、`export { ... }` を目印にして
その直前へ差し込むと、**配列が先に閉じてしまう**。

```ts
// ❌ こうなる（配列が閉じた「外」に大問が浮く → tsc が構文エラー）
  },
];            ← ここで a8_1Problems が閉じてしまっている

  {
    id: 'q_a8_1_ex2',

// ✅ 正しい
  },
  {
    id: 'q_a8_1_ex2',
```

`tsc` が `error TS1005: ';' expected.` を大量に出したら、まずこれを疑う。
確認は `grep -n "^];" <file>` で閉じ括弧の位置を数えるのが速い。
章の数と `^];` の数が一致していなければ余分に閉じている。

追記する場所は `export` の直前ではなく、
**その章の最後の大問の `},` の直後**である。

**★対戦に1問も出ない章を作ってしまう事故（実際に踏んだ）★**
演習側のテストが全部緑になっても、**対戦プールには1問も入らない**ことがある。

`a8_2` を 4大問24小問 で書き上げ、演習側の検査はすべて通ったのに、
`npm run gen:battle-pool` のあと chemistry の問題数が
**203問 のまま1問も増えなかった**。
内訳を見ると「未使用」が 194 → 218 と**ちょうど 24 件増えていた**。
書いた24小問全部が捨てられていた。

**原因**：`scripts/gen-battle-pool.mts` は
`USE_SYNTHESIZED_FORMATS === false` のため、
「元データの選択肢をそのまま使える問題」だけを採用する。
すなわち **`options` を持つ `multiple_choice`** と
**答えがカタカナの `short_answer`** の2種類だけ。
（短答・記述から誤答を借りて4択を合成する処理は、
問いとして成り立たない問題が混じるので意図的に止めてある）

`a8_2` は `multiple_choice` が **0 件**で、
`short_answer` の答えも「熱水」「硬水」など漢字だったため、
採用条件をどれも満たさなかった。

**対策**：`tests/inorganicProblems.test.ts` に
「無機化学 演習問題が対戦にも供給されている」を追加した。
- 収録した章は対戦プールに1問以上出ていること
- 寄与が3問未満の章がないこと（同じ問題ばかり当たるのを防ぐ）

このテストを入れたとき、`a8_2`（0問）に加えて
**気づいていなかった `a8_1`（2問しかない）も検出された**。

**今後の作問での預け入れ**：
各章に `multiple_choice`（`options` あり）の小問を
**最低3件**は入れる。選択式にするのに適しているのは、
「潮解と風解」「生石灰と消石灰と石灰水」のような
**紛らわしいものを並べて弁別させる**問い。
これなら対戦に供給できるし、演習としても短答より教育効果が高い。

**★`descriptive` の `gradingCriteria` は2件以上★**
1件だと「どちらか書けていれば丸」になり、自己採点の基準がぶれる。
テストが2件以上を強制している。観点は
「何に触れているか」を独立した文で分けて書く。

**★重ならないことの確認★**
化学基礎は `c1_1`(本体) + #1(443) + #2(238) + #3(181) + #4(149) = 56+1011 = **1067**
= 実測の小問計と一致。**漏れも重なりも無い。**

## 渡すときの手順（本体がやること）

1. この台帳で範囲を決め、**状態を `作業中`** にして作業場名を書く
2. `docs/battle-authoring/PROMPT.md` を開き、**§0 の枠だけ** を書き換える
   ```
   【担当範囲】     化学基礎 中盤
   【教科ID】       chemistry_basic
   【担当する章ID】 c3_1  c3_2  c3_3
   【作業場の名前】 room-cb-2
   ```
3. **ファイル全部をコピーして作業場に貼る**（ファイルを渡すのではなく本文を貼る）
4. 作業場から章ごとに JSON が返ってきたら、**状態を `受領`** にして受領した章を書く

## 受け取ったときの手順（本体がやること）

```bash
# 1) 返ってきた JSON をファイルに落とす（本体がやる。作業場はやらない）
#    src/battle/data/authored/<教科ID>.<章ID>.json

# 2) 検証（エラー0になるまで）
npm run verify:authored -- <教科ID>

# 3) 対戦プールを作り直す
npm run gen:battle-pool
#    → 「うち手書き: N 問」が増えていることを確認

# 4) 型・ビルド・テスト（★vitest の一括実行は OOM。ファイル単位で★）
npx tsc --noEmit
npx tsc -p tsconfig.scripts.json
npx vitest run tests/authoredConvert.test.ts tests/battlePool.test.ts

# 5) commit → push → PR は1つだけ
```

**分割して返ってきた場合**は、`questions` 配列を順に連結して1ファイルにする。
`id` が重複していたら **後勝ちを捨てる**（`authoredConvert` の既定と同じ）。

## やらないこと

- ❌ ZIP（`pack:authored` / `import:authored`）は **使わない**。
  作業場に ZIP を作らせる設計はやめた。スクリプト自体はリポジトリに残っているが **運用では使わない**
- ❌ 作業場に章を選ばせない
- ❌ 作業場に PR を出させない
- ❌ 章ごとに別のプロンプトを作らない（`PROMPT.md` 1本 + §0 の差し替えだけ）
